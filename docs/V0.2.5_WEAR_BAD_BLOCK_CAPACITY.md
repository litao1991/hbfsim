# HBFSim v0.2.5 Wear、Bad Block 与容量降级

## 磨损模型

`BlockMeta::erase_count` 在成功 Erase 后递增。随后该物理块的可靠性参数按线性模型计算并截断到 `[0, 1]`：

```text
Program failure probability = base_program_failure + erase_count * program_failure_per_erase
Erase failure probability   = base_erase_failure   + erase_count * erase_failure_per_erase
RBER                        = base_rber            + erase_count * rber_per_erase
```

Read Retry 在磨损后的 RBER 上继续应用 `retry_ber_multiplier^retry`。随机抽样仍由 `random_seed` 完全确定；`program_failure_budget` 仍只限制 Program Failure 注入次数。

## 退休语义

下列事件触发退休：

- Erase 抽样失败：本次请求失败，物理块进入 `Bad`；
- 成功 Erase 后 `erase_count >= max_erase_cycles`：本次 Erase 成功，但块到寿命上限并进入 `Bad`；
- `max_erase_cycles: 0` 表示不设置寿命上限。

Host-managed HBF 的分配单位是物理条带。一条 lane 的 Block 变坏后，该 physical stripe 从 free pool 和 active mapping 中永久移除，不能再分配；其它 lane 即使物理上仍可用，也不单独拼接成新条带。这保持固定交织公式和隐式 P2L 的简单性。

因此输出同时区分：

- `retired_blocks`：实际进入 Bad 状态的块数；
- `retired_stripes`：不能再分配的 Host-managed 物理条带数；
- `total_physical_capacity_bytes` 与 `usable_physical_capacity_bytes`：退休前后有效物理容量；
- `host_visible_capacity_bytes`：初始 OP 约束后的 Host 逻辑容量；
- `erase_failures`：失败 Erase 数。

当前模型没有 Spare Block remap、动态缩减 LBA namespace 或 Wear Leveling。若退休条带仍包含权威数据，Host 通过失败请求感知数据丢失/重搬需求；仿真器不隐藏恢复。

## 配置

```yaml
nand:
  reliability:
    program_failure_rate: 0
    program_failure_rate_per_erase: 1e-8
    erase_failure_rate: 0
    erase_failure_rate_per_erase: 1e-9
    raw_bit_error_rate: 1e-9
    raw_bit_error_rate_per_erase: 1e-12
    max_erase_cycles: 3000
    random_seed: 1
```
