# HBFSim v0.2.4 Automatic Refresh

## 目标与边界

Automatic Refresh 是 Host-managed 策略，而不是设备内隐藏 FTL。每个已封闭且包含有效页的条带，以第一次成功 Program 的完成时间作为 `retention_since`：

```text
deadline = retention_since + retention_time
trigger  = deadline - guard_time
```

到达 trigger 后，`RefreshManager` 按最早 deadline、再按 physical stripe id 稳定选取条带。Open、Migrating、Degraded、无有效页的条带不参与选择。

## 执行路径

刷新直接复用 `CopyEngine`：读取源条带有效 slot、顺序写入 replacement、原子 `REMAP_COMMIT`、擦除旧条带。Hole/Invalid bitmap 和 generation 规则与 Recovery、Host GC 完全一致。目标条带的首次 Program 会建立新的 retention epoch。

`TransactionSource::Refresh` 独立于显式 `Maintenance`，因此 `source_latency_breakdown.csv` 能直接比较 User、Refresh 与 GarbageCollection。默认优先级如下：

```text
critical Recovery > User Read > Recovery > User Write/Mapping
                  > Maintenance/Refresh > GarbageCollection
```

所有流量竞争相同的 Host link、DataFabric、Die、Plane、Block 和 Copy Buffer 资源；aging 仍可避免后台流量永久饥饿。Refresh 和一个 Host GC job 可以并行存在，Recovery 仍阻止新的自动 GC。

## 定时语义

`RefreshManagerWake` 只会被安排到尚未到达的 Host trace 请求之前。Trace 已结束且系统排空后，不继续人为推进时间和生成无限刷新循环。若已有刷新达到并发上限，Copy job 完成事件会重新轮询；无 replacement 时记录 deferred，超过 deadline 时记录 miss。

## 配置

```yaml
refresh:
  enabled: true
  retention_time_ns: 43200s
  guard_time_ns: 1800s
  max_concurrent_jobs: 1
```

时长字段接受裸 ns 数值以及 `ns`、`us`、`ms`、`s` 后缀。当前模型用于性能和策略竞争实验，不等价于真实 NAND 的温度加速 retention 分布。

## 输出指标

- automatic/completed/failed refresh jobs；
- deadline misses 与 no-space deferred 次数；
- Refresh Read/Program bytes；
- Refresh Copy latency 与 Copy Buffer high-watermark；
- 包含 Refresh 写流量的 stripe write amplification；
- 按 source/op 分解的排队与资源服务时间。
