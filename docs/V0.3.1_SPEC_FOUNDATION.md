# HBFSim v0.3.1 Spec Foundation

> 本文记录 v0.3.1 当时冻结的基础边界。Channel、AXI、状态码和 DLU 的后续实现分别见 v0.3.2–v0.3.5 文档；其中 v0.3.4 已完成协议数值编码绑定。

v0.3.1 建立规范导向开发所需的边界，但不把尚未实现的 HBF v0.7
命令、AXI/Channel、DLU 或错误码宣称为已兼容。当前版本的目标是让后续语义可以在
不继续扩大 `Simulator` 的前提下逐项加入，并把研究扩展与规范路径明确分开。

## Profile 与扩展边界

`simulation.profile` 支持三个值：

- `media_research`：保持 v0.3.0 行为；为兼容旧配置，三个研究扩展默认开启。
- `hbf_v0_7`：选择 HBF v0.7 规范导向路径；研究扩展默认关闭。
- `ai_system`：为后续 AI 系统工作负载语义预留；研究扩展默认关闭。

`protocol.abstraction` 在 v0.3.1 只接受 `transaction`。解析器识别 `flit`，但配置校验
会明确拒绝，以防用户误以为已经实现逐 Flit 协议时序。

研究功能必须显式位于：

```yaml
research_extensions:
  stripe_mapping: false
  copy_gc:
    enabled: false
  migration_recovery:
    enabled: false
```

旧配置未声明 Profile 时仍解析为 `media_research`，因此当前实验不会静默改变语义。
在规范 Profile 中启用研究扩展是允许的，但结果必须被标记为扩展实验，而不是纯规范结果。

## `HbfSystem` 组件边界

`HbfSystem` 是设备模型的组合根，拥有以下服务：

- `AddressMapper`
- `HostRouter`
- `ReliabilityModel`
- `HostGcManager`
- `RefreshManager`

`Simulator` 继续负责模拟时间、事件队列、资源占用和请求生命周期。为降低本次重构风险，
事件和调度代码暂时通过非拥有引用访问 `HbfSystem` 内的服务；这些引用是迁移适配层，
不再拥有组件。后续 Channel、DLU Assembler、Read Cache 和错误状态模块应加入
`HbfSystem`，而不是重新塞回 `Simulator`。

## `HbfResponse` 基础类型

`HbfResponse` 提供请求 ID、完成时间、完成字节数、语义状态和可选 `HbfErrorInfo`。
错误信息可以携带逻辑/物理地址、重试阶段、退休粒度和诊断原因。`success()` 与
`failure()` 工厂函数保证成功响应无错误负载，且失败工厂不能接收 `Success` 状态。

v0.3.1 只冻结状态的内部语义名称，不冻结数值编码。等规范条款与状态码表逐项核验后，
再在独立协议编码层绑定数值，避免把未经核验的编号写进公共模型接口。

## Spec Compliance 测试

规范相关测试独立放在 `tests/spec/`，CTest 标签为 `spec` 和 `compliance`：

- `spec_profile`：Profile 默认值、显式研究扩展、Flit 拒绝与 resolved config。
- `spec_response`：成功/失败响应不变量与错误上下文。
- `spec_system_boundary`：组件所有权边界和规范 Profile 下的基础请求回归。

可以只运行这一组测试：

```sh
ctest --test-dir build -L spec --output-on-failure
```

三个测试也进入 `tools/model_validation.py` 的默认发布门禁。

## 后续规范实现入口

v0.3.1 之后依次适合加入 HBF Channel 地址域与 Global→Channel→Local 翻译、4 KiB
DLU 聚合与 Pending DLU、Page 0 自动擦除、Read Cache/Batch Read、AXI ID 顺序，最后
把介质失败映射到 `HbfResponse`。现有 Stripe Mapping、Copy GC、Migration Recovery 和
Automatic Refresh 保留为可选研究扩展，不定义规范命令本身的语义。
